# PACER 初始角色位姿设置指南（可复用）

> 用途：在 PACER 上做自定义场景（楼梯、斜坡、指定起点）时，把角色初始位姿摆正。
> 适用版本：`pacer-main`（本次实验用的仓库）+ Isaac Gym Preview 4

---

## 一、为什么这件事很关键

PACER 是**反应式控制器**：它每一帧只根据"自身状态 + 高度图 + 未来 5 s 的 10 个路点"输出关节目标。

**它不会主动掉头。** 如果初始朝向与轨迹方向不一致，策略会先花 1–2 秒纠正；在这段时间里：

- 走得慢 → `tar_fail`（落后轨迹超过 4 m）判失败；
- 或者直接蹲下/摔倒（尤其站在台阶边缘时）。

所以：**初始位姿必须与轨迹方向一致，且必须可复现**。

---

## 二、初始位姿从哪来（代码链路）

```
humanoid_pedestrain_terrain.py : _reset_ref_state_init()
  └─ _sample_ref_state(env_ids)
       ├─ motion_ids   = self._motion_lib.sample_motions(num_envs)
       ├─ motion_times = _sample_time(motion_ids)        ← 由 stateInit 决定
       ├─ _get_fixed_smpl_state_from_motionlib(...)      ← root_pos/rot, dof_pos, 速度
       └─ [可选] 旋转区组（random_heading / start_yaw）
  ├─ new_root_xy = terrain.sample_valid_locations(...)   ← 由 --start_xy 覆盖
  ├─ root_pos[2] += center_height                        ← 按高度图抬到地面
  └─ _set_env_state(root_pos, root_rot, dof_pos, ...)    ← 直接写入 tensor
```

### 两个必须先固定的开关（`pacer/data/cfg/pacer.yaml`）

```yaml
stateInit: "Start"            # 关键！Random 会让每次运行的初始姿态都不同
has_upright_start: True       # 关键！必须 True，False 会让物理里的身体横躺
```

| 开关 | 取值 | 影响 |
|---|---|---|
| `stateInit` | `Random`（默认） | 从参考动作里**随机**取一帧 → 每次结果不同，A/B 对比失效 |
| | `Start` | 固定取第 0 帧 → **可复现**，做实验必须用这个 |
| `has_upright_start` | `True` | ✅ **本仓库必须用这个**：物理中的身体才是直立的 |
| | `False` | ❌ 初始位姿按 SMPL base rotation 摆放 → **物理中身体横躺**，而观测又把它补偿回直立 → 策略与物理解耦 |

> ⚠️ **2026-11-02 修正**：本文早期版本写的是 `False`，那是被"dump 重放看起来是对的"误导得出的结论。
> 实测 `False` 时 200 帧重置 15 次、身体横着坠落；改 `True` 后重置 1 次、走完整段 5 级楼梯。
> 完整证据链见 [根因-has_upright_start.md](根因-has_upright_start.md)。

## 三、三个坐标约定陷阱（最耗时的地方）

### 陷阱 1：四元数分量顺序

| 来源 | 顺序 |
|---|---|
| Isaac Gym 的 `root_states[3:7]` | **(x, y, z, w)** |
| scipy `Rotation.as_quat()` | (x, y, z, w) |
| PACER 自己的 `torch_utils.calc_heading_quat` 等辅助函数 | 按 **(w, x, y, z)** 使用 |

**后果**：用 `(w,x,y,z)` 去构造 z 轴旋转，`yaw=0` 会得到 `(0,0,0,1)`，被当成 180° 旋转——正是本会话中"设 0° 结果转了 180°"的原因。

**正确写法（相对旋转，单位四元数）**：

```python
half = float(yaw_rad) / 2.0
zero = torch.zeros(num_envs, device=self.device, dtype=root_rot.dtype)
cos_h = torch.full((num_envs,), float(np.cos(half)), device=..., dtype=...)
sin_h = torch.full((num_envs,), float(np.sin(half)), device=..., dtype=...)
q_rot = torch.stack([zero, zero, sin_h, cos_h], dim=-1)   # (x, y, z, w)
```

### 陷阱 2：SMPL 的 base rotation

```python
base_rot = quat_conjugate(torch.tensor([[0.5, 0.5, 0.5, 0.5]]))
```

`(0.5,0.5,0.5,0.5)` 是**绕 (1,1,1) 转 120°**，它把 **+x 轴映射到 +y** —— 其"航向分量"正好 **90°**。

因此：

- **body +X 轴**（观测里 `calc_heading` 用的）与**视觉正面**（人的脸朝向）之间存在约 90°~180° 的固定偏差；
- 用某个量"测朝向"时，一定要说清楚测的是哪个：body +X / 视觉正面 / 位移方向，三者不同。

### 陷阱 3：辅助函数混用

`torch_utils.my_quat_rotate` / `calc_heading_quat` 与 Isaac Gym 的 `quat_apply` / `quat_mul` 约定不同，混用会得到"看起来像随机"的结果。

**建议**：需要做几何计算时，统一只用 Isaac Gym 的 `quat_apply` / `quat_mul`，自己用 `atan2` 算航向：

```python
ref = torch.zeros((N, 3), device=dev, dtype=dt); ref[:, 0] = 1.0
d = quat_apply(root_rot, ref)              # body +X 在世界系的方向
heading = torch.atan2(d[:, 1], d[:, 0])
```

## 四、旋转初始位姿的正确做法

在 `_sample_ref_state` 里，**得到参考姿态之后**整体旋转：

```python
# 1) 构造绕 z 的相对旋转四元数（x,y,z,w）
q_rot = torch.stack([zero, zero, sin_h, cos_h], dim=-1)

# 2) 旋转朝向
root_rot = quat_mul(q_rot, root_rot).clone()

# 3) 旋转刚体位置：绕根位置转，**必须把 root_pos 加回去**
q_rep = q_rot[:, None].repeat(1, 24, 1)
rb_pos = (quat_apply(q_rep, rb_pos - root_pos[:, None, :]) + root_pos[:, None, :]).clone()
key_pos = (quat_apply(q_rep[:, :4, :], key_pos - root_pos[:, None, :])
           + root_pos[:, None, :]).clone()

# 4) 旋转刚体朝向与角速度
rb_rot = quat_mul(q_rep, rb_rot).clone()
root_ang_vel = quat_apply(q_rot, root_ang_vel).clone()
```

> ⚠️ **PACER 原代码在 `random_heading` 分支里漏了第 3 步的 `+ root_pos`**，
> 一旦启用旋转，所有刚体被平移到原点附近，角色一出生就散架。
> 这个 bug 在默认配置下不会暴露（`random_heading` 默认关闭）。

## 五、校准流程（SOP）

因为存在 base rotation 的固定偏差，**不要试图从头推导角度，直接标定**：

```
① 固定 stateInit = Start
② 跑一次 yaw = 0，渲染"第 0 帧"，读出视觉正面方向 φ0
③ 目标方向 φ_target（= 轨迹方向）
④ 需要的相对旋转 Δ = φ_target − φ0
⑤ 设 --start_yaw = Δ（弧度），再跑一次
⑥ 确认第 0 帧正面 ≈ φ_target
```

**映射是 1:1 线性的**（已验证），所以通常一次就能到位。

### 实测标定数据（本仓库、本 checkpoint）

不同版本的旋转实现斜率不同，**换实现要重新标定**：

| 请求 `start_yaw` | 视觉正面（脚趾−脚踝） | 备注 |
|---|---|---|
| 0° | −20.7° | 修正四元数顺序后 |
| **90°** | **69.7°** | ✅ **已验证为正确值**（+90.4°，线性 ✓） |
| 202.3° | −179.1° | ≈180°（理论上对准 −x） |

（早期错误实现下的数据：0°→64.2°、90°→12.4°、180°→−60.2°，斜率约 −0.7，**非线性**——这就是实现有 bug 的信号。）

### ✅ 结论：`--start_yaw 1.5708`（90°）

在以下场景中，**90° 已被确认是正确的人体位姿**：

| 项 | 值 |
|---|---|
| 地形 | `stairs05_neg`（5 级楼梯，沿 **−x** 下降，落差 0.75 m） |
| 出生点 | `--start_xy "0.0,0.0"`（平台顶） |
| 路径 | `data/paths/stairs05_neg.json`（沿 **−x**） |
| 初始位姿 | `--start_yaw 1.5708`（**90°**，相对旋转） |

> 90° 与 112.3° 的数值结果几乎相同（dx = −0.28、dz = −0.47、7 次重置），
> 但**画面上 90° 的朝向才是对的**——这也说明"看数值猜朝向"不可靠，必须看渲染帧。
> 后续所有自定义场景，**默认从这个 90° 起步**，只需按新地形方向增减。

## 六、验证方法（别再用"看起来对不对"）

### 方法 0：先确认"你看的是不是真相"（铁律，优先级最高）

**判断角色姿态，只能看仿真相机；不能用 dump 反算重放。**

```bash
# ✅ 真相源：Isaac Gym 渲染（auto_record 相机）
bash script/run_stairs.sh --mesh stairs05_neg --yaw 1.5708 --frames 200 --tag check
#    -> experiment_result/check/auto.mp4

# ❌ 会骗人：root+dof 反算重放（它只反映 dump 记录了什么）
python script/render_path.py --states X.pkl --out replay.mp4
```

原因：`_dump_auto_record()` 存的是**观测侧**张量（`_humanoid_root_states` / `_rigid_body_pos`），
而视频是仿真渲染。二者在 `has_upright_start` 配错时会**互相矛盾**：dump 看着直立，实际横躺。
详见 [根因-has_upright_start.md](根因-has_upright_start.md)。

**解耦信号**：如果改路径长度 / `--start_yaw` / 摔倒判定 / 把策略输出置零，轨迹却**逐帧几乎不变**，
说明控制回路已断，别再调参数，先查状态一致性。

### 方法 A：可视化（最直观）

用 `script/render_path.py` 渲染第 0 帧，同时画出：

- 紫红折线 = 轨迹 `traj_verts`
- 黄色点 = 策略当帧看到的 10 个路点
- 白圈 = 根位置

**判据**：第 0 帧里角色正面朝向应与折线延伸方向一致。

> 注意：方法 A 验证的是"dump 里记录的 root+dof 所对应的姿态"，
> 不等于仿真真实姿态。要确认仿真里的姿态，必须回到方法 0。

### 方法 B：数值（可入库做回归）

```python
# body +X 的世界朝向
ref = torch.zeros((N,3)); ref[:,0] = 1
d = quat_apply(root_rot, ref)
heading = degrees(atan2(d[:,1], d[:,0]))
```

> 注意：`脚趾−脚踝` 向量只有在**双脚落地**时才可靠；帧 0 若还在下落/摆动，读数会偏。

**本仓库实测标定值**（2026-11-02，`stairs05_neg`，脚本 `script/check_heading.py`）：

| `--start_yaw` | body +X | 视觉正面（双脚均值） |
|---|---|---|
| 0° | +82.7° | +88.5° |
| 90° (1.5708) | +173.0° | **+177.7°** |

斜率 0.99（1:1 线性 ✓）。轨迹方向 −180° → 残差 **2.3°**，`1.5708` 正确。

### 方法 C：位移方向（滞后但最诚实）

跑 1–2 秒，看 `dx, dy` 的方向是否与轨迹方向一致。缺点是要等角色动起来。

## 七、坑位清单（Checklist）

跑自定义场景前逐条核对：

- [ ] `stateInit: "Start"`（不是 Random）
- [ ] **`has_upright_start: True`**（用 False 物理里的身体会横躺，且观测看不出来）
- [ ] **判姿态用的是 auto_record 视频，不是 render_path 重放**（方法 0）
- [ ] 旋转四元数按 **(x, y, z, w)** 构造
- [ ] 旋转 `rb_pos` 时**加回了 `root_pos`**
- [ ] `rb_rot` / `root_ang_vel` 同步旋转
- [ ] 用 `--start_xy` 固定出生点，且落在平台/地面内部（离边缘 > 脚长）
- [ ] 出生点高度由 `center_height` 自动修正，不要手动给 z
- [ ] **路径隐含速度**在 0.8–1.2 m/s（= 路径总长 / episode 时长）
- [ ] 第 0 帧渲染确认：正面与轨迹同向

## 八、与其他问题的边界

初始位姿摆正**只解决"起点"问题**，以下问题与它无关，不要混为一谈：

| 现象 | 是否与初始位姿有关 |
|---|---|
| 角色原地蹲下不动 | 可能有关（朝向反了 / 目标太近） |
| 横向漂移走出楼梯 | **另有原因**（观测/控制），本会话未定位 |
| 走两步后摔倒 | 多半与步子/地形/终止判定有关 |
| 目标点太近（路点只铺 0.36 m） | **路径速度问题**，与位姿无关 |

## 九、最小可复用代码片段

```python
# ---- 在任何 task 的 _sample_ref_state 末尾加入 ----
import numpy as np
import torch

def rotate_initial_pose(root_pos, root_rot, rb_pos, key_pos, rb_rot, root_ang_vel,
                        yaw_rad: float, device):
    """把初始位姿整体绕 z 轴旋转 yaw_rad（相对旋转）。"""
    n = root_rot.shape[0]
    half = float(yaw_rad) / 2.0
    zero = torch.zeros(n, device=device, dtype=root_rot.dtype)
    cos_h = torch.full((n,), float(np.cos(half)), device=device, dtype=root_rot.dtype)
    sin_h = torch.full((n,), float(np.sin(half)), device=device, dtype=root_rot.dtype)
    q_rot = torch.stack([zero, zero, sin_h, cos_h], dim=-1)      # (x,y,z,w)

    root_rot = quat_mul(q_rot, root_rot).clone()

    q_rep = q_rot[:, None].repeat(1, rb_pos.shape[1], 1)
    rb_pos = (quat_apply(q_rep, rb_pos - root_pos[:, None, :])
              + root_pos[:, None, :]).clone()
    key_pos = (quat_apply(q_rep[:, :4, :], key_pos - root_pos[:, None, :])
               + root_pos[:, None, :]).clone()
    rb_rot = quat_mul(q_rep, rb_rot).clone()
    root_ang_vel = quat_apply(q_rot, root_ang_vel).clone()
    return root_pos, root_rot, rb_pos, key_pos, rb_rot, root_ang_vel
```

调用（本仓库实测值，目标：面朝 −x 下楼梯）：

```yaml
# 命令行
--start_xy "0.0,0.0" --start_yaw 1.5708    # 90°，约等于对准 −x
```
